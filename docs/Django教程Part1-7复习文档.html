全景Django 是什么、请求怎么走完一圈

Django 是一个「电池全带」（batteries-included）的 Web 框架：管理后台、用户认证、ORM、模板、表单、静态文件……开箱即用。它遵循 MVT 模式，和 MVC 是一回事，只是名字不同：

MVC 说法Django 说法对应文件
Model（模型）Model（模型）reviews/models.py
View（视图）Template（模板）reviews/templates/reviews/*.html
Controller（控制器）View（视图）reviews/views.py + reviews/urls.py

面试常被要求「口述一次请求的完整流程」。以你项目里真实的例子 /album/5/ 为例：

1. 浏览器发出请求　GET /album/5/
↓
2. WSGI 入口　music_review/wsgi.py（开发时由 runserver 启动）
↓
3. 项目总路由　music_review/urls.py → path('', include('reviews.urls')) 把请求分发给 reviews 应用
↓
4. 应用路由　reviews/urls.py → path('album/<int:album_id>/', views.album_detail) 解析出 album_id = 5
↓
5. 视图执行逻辑　views.album_detail(request, album_id=5)
↓
6. 模型读写数据库　get_object_or_404(Album, id=5)、album.ratings.all() → 查询 db.sqlite3
↓
7. 渲染模板　render() 用 reviews/album_detail.html + 上下文变量拼出 HTML
↓
8. 返回响应　HttpResponse（HTML）送回浏览器

项目 vs 应用

通俗比喻：项目 = 整座商场（骨架、水电、总服务台），应用 = 商场里的商铺（各自独立的功能模块）。一个项目可以装多个应用。

项目（music_review）应用（reviews）
创建命令django-admin startproject music_reviewpython manage.py startapp reviews
职责全局配置 settings.py、总路由、部署入口具体功能：模型、视图、模板、后台
复用一般不复用理论上可以装到别的项目里

你以后要加「用户系统」时，正确的做法是再建一个应用（如 users），而不是把登录代码全塞进 reviews——应用是 Django 的模块化单位。

1.3 知识点精讲

manage.py 和 django-admin 的区别

命令区别何时用
django-admin全局命令，不知道你项目在哪，需要显式指定 settings创建项目：django-admin startproject xxx
python manage.py自动绑定了当前项目的 settings 和环境，还会把项目根目录加入 Python 路径项目内的一切操作：runserver、startapp、makemigrations、migrate、shell、test…

记忆口诀：「建项目找 django-admin，进项目后一律 manage.py」。

视图 = 一个函数（或类），吃进请求、吐出响应

✍️ 视图函数的"合同"
  • 第一个参数必须是 request（HttpRequest 对象，携带了方法、路径、GET/POST 参数等全部请求信息）；
  • 返回值必须是 HttpResponse（或其子类：JsonResponse、Http404 抛出前……）；
  • 教程第一版写法 return HttpResponse("Hello, world") 返回的是纯文本，后来换成 render() 才返回真正的 HTML 页面——你项目里 4 个视图用的全是 render()。

path() 的四个参数

path(route, view, kwargs=None, name=None)——重点是 route 和 name：

  • route：URL 模式。尖括号是「路径转换器」，如 <int:album_id> 表示"这里匹配一段整数，作为参数 album_id 传给视图"。Django 会自动把字符串转成整数。
  • name：给这条路由起名字。模板里 {% url 'album_detail' album.id %} 靠它反查 URL——以后改 URL 结构，模板不用动（第 3 章细讲）。
转换器匹配内容乐评项目里的用法
int非负整数（0,1,2…）<int:album_id> → /album/5/
str除 / 外的任意字符串（默认转换器，可省略）<str:artist_name> → /artist/周杰伦/
slug字母、数字、连字符、下划线（适合做网址别名）将来给专辑加 slug 可以用
uuidUUID 格式一般用于对外 API
path含 / 的完整路径很少用
⚠️ 中文 URL 的小细节

你的 /artist/周杰伦/ 能工作，是因为浏览器会自动把中文 URL 编码（URL encode）再发送，Django 解码后再匹配 str 转换器。所以 str 转换器对中文是安全的。

include() 的作用：分权

总路由只做「分流」，把以某前缀开头的 URL 整体交给某个应用。好处：应用自带路由文件，解耦、可插拔——将来把 reviews 应用搬到另一个项目，路由文件跟着走就行。面试可以答：include 实现了 URL 配置的模块化。

runserver 的实用细节

  • 自动重载：改代码保存后服务器自动重启，不用手动重启（改 settings 有时要手动）。
  • 换端口：python manage.py runserver 8080。
  • 手机访问（同一个 Wi-Fi 下）：python manage.py runserver 0.0.0.0:8000，再用电脑的局域网 IP（如 192.168.x.x:8000）从手机访问——调试移动端页面很常用。注意默认 ALLOWED_HOSTS = [] 只放行本机，局域网访问需要把它改为 ['*'] 或你的局域网 IP（仅开发时用）。
  • 尾斜杠：Django 默认 APPEND_SLASH = True，访问 /album/5 会自动 301 重定向到 /album/5/。

1.4 常见错误

🚫 新手高频错误
  • 视图函数没有 return → 报 The view didn't return an HttpResponse object. It returned None instead.
  • 忘了把应用加进 INSTALLED_APPS / 忘了 include 应用路由 → 页面 404，而你以为代码写错了。
  • path 里转换器类型写错：<int:album_id> 访问 /album/abc/ 会 404，因为 abc 不是整数——这是故意的，Django 在帮你挡非法输入。
  • 两个应用定义了同名 name（如都叫 home）→ 用 {% url %} 反查时冲突，解决办法是命名空间（第 3 章讲 app_name）。

reviews/models.py（你的完整模型）
import requests
from django.db import models
from django.core.validators import MinValueValidator, MaxValueValidator

class Album(models.Model):
    title = models.CharField(max_length=200)
    artist = models.CharField(max_length=200)
    release_date = models.DateField()
    cover_url = models.URLField(blank=True)
    genre = models.CharField(max_length=100, blank=True)
    label = models.CharField(max_length=100, blank=True)
    critic_score = models.IntegerField(blank=True, null=True,
        validators=[MinValueValidator(0), MaxValueValidator(100)])
    critic_review = models.TextField(blank=True)
    critic_name = models.CharField(max_length=100, blank=True)
    critic_published_at = models.DateField(null=True, blank=True)

    def __str__(self):
        return f"{self.title} - {self.artist}"

    def fetch_cover_from_itunes(self):
        """从 iTunes API 获取专辑封面（无需 API 密钥）"""
        url = 'https://itunes.apple.com/search'
        params = {'term': f'{self.artist} {self.title}',
                  'media': 'music', 'entity': 'album', 'limit': 1}
        try:
            response = requests.get(url, params=params, timeout=5)
            response.raise_for_status()
            data = response.json()
            if data['resultCount'] > 0:
                cover_url = data['results'][0]['artworkUrl100'].replace('100x100', '1000x1000')
                self.cover_url = cover_url
                self.save()
                return cover_url
        except Exception as e:
            print(f"iTunes 获取封面失败：{e}")
        return None

class UserRating(models.Model):
    album = models.ForeignKey(Album, on_delete=models.CASCADE, related_name='ratings')
    score = models.IntegerField(validators=[MinValueValidator(0), MaxValueValidator(10)])
    reviewer_name = models.CharField(max_length=100, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        name = self.reviewer_name or "匿名用户"
        return f"{name} - {self.album.title} - {self.score}分"

你项目的迁移史——理解迁移机制的最佳素材

你的 reviews/migrations/ 里有 6 个迁移文件，串起来就是你模型设计的演进史：一开始乐评和用户评分共用一个 Review 表，后来发现乐评信息更适合放进 Album，于是把字段搬了家、把表改了名：

💡 这个演进史说明了什么

迁移机制的核心价值：模型可以放心大胆地改（加字段、删字段、改名），数据库结构跟着版本化演进，且每一步都可回滚、可追溯。没有迁移的框架里，改表结构要手写 SQL 手动同步，很容易把数据搞坏。

字段参数：blank 和 null 的区别（面试必考！）

参数管的是哪一层含义什么时候用
blank=True表单校验层（admin 表单、ModelForm）允许提交时留空「可选填」的字段
null=True数据库层允许数据库里存 NULL「可以没有值」的字段
💡 经验法则（你项目里就是这么做的）
  • 字符串字段（CharField/TextField）留空时数据库存的是空字符串 ''，不需要 NULL，所以只写 blank=True 就够；
  • 数字、日期、外键字段（IntegerField/DateField/ForeignKey）没有"空字符串"这个概念，留空就必须存 NULL，所以 blank=True 和 null=True 两个都要写——看你的 critic_score：blank=True, null=True 双写，正确！
  • 一句话总结：blank 管表单，null 管数据库。

其他高频参数

参数作用你项目里的例子

⚠️ validators 的一个大坑（重要）

validators 只在表单校验时触发——也就是你在 admin 后台保存数据时会拦住超范围的分数。但直接写代码 UserRating(score=99).save() 是不会报错的，数据库里照样存进 99 分！想强制校验必须调用 obj.full_clean()。面试问到「Django 的字段验证发生在哪一层」时，这个点能帮你加分。

ForeignKey：一对多关系

  • 语义：一张专辑可以有多个用户评分，一个评分只属于一张专辑。所以「多」的那一方（UserRating）持有外键。
  • on_delete：专辑被删除时，关联的评分怎么办？
on_delete 选项行为
CASCADE（你用的）级联删除：删专辑，它的评分一起删
PROTECT禁止删除：还有评分就删不掉专辑，抛 ProtectedError
SET_NULL置空：外键设为 NULL（要求 null=True）
SET_DEFAULT设为默认值
DO_NOTHING什么都不做（可能产生孤儿数据，慎用）
  • related_name='ratings'：给「反向关系」起名。默认反向名是 userrating_set，你自定义成 ratings 后，查询更顺口：album.ratings.all() 而不是 album.userrating_set.all()。视图和模板里都在用它，所以第 4 次迁移里把 related_name 从 reviews 改成 ratings 时，代码里所有引用也要跟着改——这正说明 related_name 是「代码接口」而不仅是数据库概念。

__str__ 方法的作用

决定这个对象怎么自我介绍：admin 列表页里显示什么、shell 里 print 出来什么。没有它，admin 里全是难看的 "Album object (5)"。

模型不只是字段，还可以带行为

你的 fetch_cover_from_itunes() 是教程里 was_published_recently() 的加强版：模型方法可以调用外部 API、修改自身字段。注意它内部的 self.save() 只是普通的数据库保存，不会回头触发 admin 的 save_model——因为 save_model 是 admin 的钩子，只在你点后台"保存"按钮时执行一次。这个区分在第 7 章还会用到。

迁移：三步走 + 原理

改 models.py → python manage.py makemigrations → python manage.py migrate
  • makemigrations：对比模型和已有迁移文件，生成新的迁移文件（"改动说明书"）。只生成，不动数据库。
  • migrate：按顺序执行迁移文件里的操作，真正改数据库。Django 会记录哪些迁移已执行（django_migrations 表），所以重复执行是安全的。
  • 为什么要分两步？因为迁移文件是代码，要提交到 Git 给团队共享；同事 pull 到迁移文件后自己跑 migrate，就能把数据库同步到同一版本。分两步 = 改动能被版本管理。
  • 辅助命令：python manage.py sqlmigrate reviews 0001 查看某个迁移会执行什么 SQL；python manage.py showmigrations 看执行状态（[X] 已执行）。

💡 get 和 filter 的根本区别

get() 返回一个对象，找不到就抛异常（多条匹配也抛 MultipleObjectsReturned）；filter() 返回集合，找不到就是空集合，不会报错。所以「可能不存在」的场景，教程推荐 get_object_or_404()：存在就返回对象，不存在就抛 Http404 显示 404 页——你的 album_detail 就是这么写的。

3.3 知识点精讲

render() 的三个参数

render(request, '模板路径', 上下文字典)：① 请求对象；② 模板路径；③ 传给模板的变量字典（可选，缺省为空字典）。它做的事 = 加载模板 + 用上下文渲染 + 打包成 HttpResponse 返回。对比：

写法返回内容什么时候用
HttpResponse("纯文本")纯文本调试、极简接口
render(request, 'xxx.html', {...})渲染后的 HTML绝大多数页面
redirect('路由名', 参数)302 跳转响应操作成功后跳走（第 4 章 PRG 模式）

模板是怎么被找到的：命名空间约定

你的 settings 里 APP_DIRS: True，Django 会去每个已安装应用的 templates/ 目录找模板。为什么路径是 reviews/home.html 而不是 home.html？——因为各应用的 templates 目录是「平铺」的，如果两个应用都有 home.html 就会打架。所以在应用 templates 下再包一层和应用同名的子目录做命名空间：

reviews/templates/reviews/home.html
reviews/templates/reviews/album_detail.html
reviews/templates/reviews/artist_albums.html
reviews/templates/reviews/critic_albums.html

DTL 模板语言三件套

语法作用你的项目里的例子
{{ 变量 }}输出变量的值{{ album.title }}
{% 标签 %}逻辑控制{% for %} / {% if %} / {% url %} / {% empty %}
{{ 值|过滤器 }}加工输出格式{{ release_date|date:"Y-m-d" }}

模板里的点号查找规则（经典考点）

{{ album.ratings.count }} 里的点号，Django 按这个顺序解析：① 字典的 key → ② 对象的属性 → ③ 对象的方法（自动调用，不加括号）→ ④ 列表索引。所以模板里写 .count 不用加括号（加了也会被忽略），而 Python 的 len() 函数在模板里必须换成过滤器 {{ albums|length }}——你 home.html 里就是这么写的。这也是 DTL「设计哲学」的体现：模板里只能展示数据，不能写业务逻辑（不能定义变量、不能任意调用带参数的函数）。

get_object_or_404 的原理

它等价于：

try:
    album = Album.objects.get(pk=album_id)
except Album.DoesNotExist:
    raise Http404("No Album matches the given query.")

Http404 异常被 Django 捕获后返回 404 页面（DEBUG=True 时是带调试信息的 404 页）。你的 album_detail 用它，访问 /album/999/ 会得到干净的 404 而不是 500 报错页——这是「用户可能输入不存在的 id」场景的标准写法。

写法问题 / 优点
硬编码 href="/album/{{ album.id }}/"路由一变，所有模板都要改，极易漏改
{% url 'album_detail' album.id %}按 name 反查 URL，路由怎么改模板都不用动

带参数的 name 直接跟在后面：{% url 'artist_albums' album.artist %}。你四个页面的所有跳转链接（艺人页、乐评人页、详情页、返回首页）全部用的 url 标签，正确。

GET vs POST 分工（面试必考）

CSRF：为什么 POST 表单必须带 {% csrf_token %}

攻击场景：恶意网站伪造一个指向你网站的 POST 表单，诱导已登录用户点它，浏览器会自动带上你网站的 Cookie，于是攻击者能以用户身份执行操作（比如用你的账号发评论）。Django 的防御：POST 表单里放一个随会话生成的一次性令牌（hidden input），提交时中间件（CsrfViewMiddleware，你 settings 里就有）核对令牌与 Cookie 是否匹配——伪造网站拿不到这个令牌。

操作层面：凡是 POST 表单，<form> 里必须写 {% csrf_token %}；忘了就报 403 CSRF verification failed。排查顺序：① 表单里有没有 csrf_token；② settings 里 CsrfViewMiddleware 在不在。

PRG 模式：提交成功后必须重定向

POST　用户提交评分表单 → 视图处理：创建 UserRating
↓
Redirect　视图返回 redirect('album_detail', album_id=album.id)（302 跳转）
↓
GET　浏览器重新请求详情页 → 用户看到新评分已出现在列表里

为什么不能直接 render 结果页？因为浏览器地址栏还是 POST 地址，用户一按 F5 就重复提交一次评分。先重定向，地址变成 GET，刷新就安全了。口诀：「写操作成功 → 重定向到读页面」。

视图里怎么接收表单数据

接收 POST 数据 + PRG 的骨架（将来评分视图的雏形）
def add_rating(request, album_id):
    album = get_object_or_404(Album, id=album_id)

    if request.method == 'POST':
        score = request.POST.get('score')
        reviewer_name = request.POST.get('reviewer_name', '')
        UserRating.objects.create(
            album=album, score=score, reviewer_name=reviewer_name)
        return redirect('album_detail', album_id=album.id)   # PRG！

    return render(request, 'reviews/add_rating.html', {'album': album})

要点：request.method 区分请求类型；request.POST.get('score') 取表单值（POST 是 QueryDict，get 带默认值更安全）；UserRating.objects.create(...) 一步完成「建对象 + 存库」。真实项目里这里还要做校验（分数是否 0–10、用户是否已评过），那是下一步用户系统的事。

通用视图（CBV）：为什么教程要重写成类视图

函数视图里「列表页 = 查一堆 + 渲染」「详情页 = 查一个 + 渲染」是非常重复的模式。Django 提供了一组类视图（ListView、DetailView、CreateView、UpdateView、DeleteView），把常用流程封装好，你只需要声明少量属性：

属性ListViewDetailView
model =Album（自动查全部）Album（自动按主键查一个）
template_name默认 app/模型_list.html默认 app/模型_detail.html
context_object_name默认 album_list默认 album（模型名小写）
pk_url_kwarg—URL 里的主键参数名，默认 'pk'
可覆写的方法get_queryset()（自定义查询）get_context_data()（补充上下文）

路由写法从函数换成类：path('', views.AlbumListView.as_view(), name='home')。as_view() 是类视图的入口：它把类实例化并转成一个可调用的函数视图（内部按请求方法分发到 get/post 方法）。

把乐评项目两个视图改写成 CBV（参考实现）

from django.views import generic

class AlbumListView(generic.ListView):
    model = Album
    template_name = 'reviews/home.html'
    context_object_name = 'albums'

    def get_queryset(self):
        query = self.request.GET.get('q', '').strip()
        albums = Album.objects.all()
        if query:
            albums = albums.filter(
                Q(title__icontains=query) | Q(artist__icontains=query))
        return albums

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context['query'] = self.request.GET.get('q', '')   # 模板还要用 query
        return context
album_detail → AlbumDetailView（平均分放进 get_context_data）
class AlbumDetailView(generic.DetailView):
    model = Album
    template_name = 'reviews/album_detail.html'
    pk_url_kwarg = 'album_id'      # 你的路由参数叫 album_id，不是默认的 pk！

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        avg_score = self.object.ratings.all().aggregate(Avg('score'))['score__avg']
        context['avg_score'] = round(avg_score, 1) if avg_score is not None else None
        return context
💡 注意一个细节

你的路由写的是 <int:album_id>，而 DetailView 默认从 pk 参数取主键，所以必须显式写 pk_url_kwarg = 'album_id'。这是「路由参数名和类视图约定不一致」时最常见的坑。

🧠 函数视图 vs 类视图怎么选（面试点）
  • 函数视图：逻辑简单直白，一眼看到底，适合流程特殊的页面（你的搜索、艺人页、乐评人页用函数视图完全合理）；
  • 类视图：能复用通用流程（列表/详情/增删改查），继承 + 覆写即可，代码更少，但调用链深、调试略绕；
  • 结论：不要为了用 CBV 而用 CBV，标准 CRUD 用 CBV，特殊流程用函数视图。面试被问「你项目里为什么有的用函数有的用类」，能这样答就是加分。

4.4 常见错误

🚫 新手高频错误
  • POST 表单忘写 {% csrf_token %} → 403 Forbidden，很多人以为是权限问题。
  • 搜索表单用 method="post" → 语义错误 + 刷新弹确认框 + 无法分享链接。
  • POST 处理后直接 render → 刷新重复提交（缺 PRG）。
  • DetailView 没配 pk_url_kwarg → 404，因为它在 URL 里找不到叫 pk 的参数。
  • 表单字段的 name 和视图取值的 key 不一致（表单 name="q"，视图却 get('query')）→ 静默拿到 None。

5.3 知识点精讲

为什么必须写测试（面试必问，背这套话术）

  1. 回归保护：功能越改越多，人脑记不住所有行为。测试跑一遍 = 自动确认「老功能没被我改坏」。
  2. 重构的信心：上一章的 CBV 改造为什么敢做？因为测试全绿就说明行为没变。没有测试的重构叫赌博。
  3. 活的文档：测试写着「首页搜索"周杰伦"时只返回周杰伦的专辑」，这就是需求说明。
  4. 省时间：手动点页面验证一次 2 分钟，100 次就是 200 分钟；测试 1 秒跑完，永远复用。

Django 测试的运行机制

  • TestCase 类：继承 django.test.TestCase，每个以 test_ 开头的方法就是一个测试。
  • 独立测试数据库：跑测试时会创建一个全新的临时数据库，跑完销毁——绝不碰你的开发数据（db.sqlite3 安然无恙）。测试里需要的数据在 setUp() 里现造。
  • 断言（assert）：一条测试 = 造数据 → 执行 → 断言结果符合预期。断言失败 = 测试红，全部通过 = 测试绿。

6.2 乐评项目现状

⚠️ 诚实对照

你的 4 个模板目前全是内联样式（style="..." 直接写在标签上），项目里还没有 static 目录。内联样式能跑，但有三个问题：① 每个页面重复写；② 改样式要翻遍所有标签；③ 无法复用（比如「专辑卡片」的样式在首页和详情页都要用）。这一章的练习就是把内联样式收敛到一个 style.css 里。

6.3 知识点精讲

静态文件 vs 模板：本质区别

模板（.html）静态文件（.css/.js/.png）
内容带 {{ }} {% %} 的动态内容固定内容，原样发给浏览器
存放templates/reviews/static/reviews/
服务方式Django 渲染后输出直接以文件形式返回，URL 形如 /static/...

目录约定（和模板命名空间一模一样）

reviews/static/reviews/style.css      ← 应用内静态目录，同样要包一层 reviews/ 子目录

原因同模板：各应用的 static 目录是平铺合并的，不包子目录的话两个应用都叫 style.css 就会互相覆盖。

引用方式：{% static %} 标签

base.html 里引入样式（先 load 再用）
{% load static %}

<link rel="stylesheet" href="{% static 'reviews/style.css' %}">

{% load static %} 加载标签库（每个用它的模板都要写一次，或放在 base.html 顶部）；{% static '路径' %} 由 Django 拼接成 /static/reviews/style.css——以后 STATIC_URL 变了，所有引用自动跟着变，这就是「不硬编码」的意义。

开发 vs 生产：静态文件的分水岭（面试常考）

  • 开发阶段（DEBUG=True）：django.contrib.staticfiles 应用（你 INSTALLED_APPS 里有）自动帮你把各应用的静态文件通过 /static/ 提供出去，什么都不用配。
  • 生产阶段（DEBUG=False）：Django 不再自动服务静态文件（性能和安全考虑，交给 Nginx）。需要两步：
# settings.py 增加
STATIC_ROOT = BASE_DIR / 'staticfiles'

# 终端执行：把所有应用的静态文件收集到一个目录
python manage.py collectstatic

然后让 Nginx 直接服务 STATIC_ROOT 目录。相关配置：STATIC_URL（访问前缀，你的 settings 里是 'static/'）、STATICFILES_DIRS（额外的静态目录，非必须）。调试用 python manage.py findstatic reviews/style.css 可以确认文件到底放在哪。

6.4 常见错误

🚫 新手高频错误
  • CSS 不生效（404）：① 忘了 {% load static %}（报模板语法错误）；② 路径漏了 reviews/ 子目录；③ 文件放到了 templates 目录里（放错阵营）。
  • 浏览器缓存：改了 CSS 页面没变化，试试 Ctrl+F5 强刷。
  • 生产环境静态文件全 404：DEBUG=False 后没跑 collectstatic、没配 Nginx——这是部署第一大坑，你学习计划「第五阶段」部署时会正面遇到。

                f'<img src="{obj.cover_url}" width="50" height="50"'
                f' style="object-fit: cover;" />')
        return "无封面"
    cover_preview.short_description = '封面'
  • 原理：list_display 里的名字如果不是模型字段，Django 就去找 ModelAdmin 上的同名方法，把每个对象传进去（obj 参数），返回值显示在那一列。
  • mark_safe 的作用：Django 默认会把方法返回的字符串转义（<img> 会原样显示成文本），mark_safe 声明「这段字符串是安全的 HTML，直接渲染」。所以要显示图片，必须 mark_safe。
  • short_description：列的标题，不加的话列名就是方法名 cover_preview。
⚠️ mark_safe 的安全边界（面试加分点）

mark_safe 会绕过转义保护，如果拼接的内容包含用户输入就可能被注入脚本（XSS）。你的封面 URL 来自 iTunes API 而不是用户输入，风险可控；但更好的习惯是用 format_html（你 admin.py 顶部已经 import 了它却没用）：format_html('<img src="{}" />', obj.cover_url) 会自动转义参数、只信任模板部分，安全性更高。面试时说「我用 format_html 而不是裸 mark_safe」能体现安全意识。

③ 自定义筛选器：SimpleListFilter

reviews/admin.py 节选
class ScoreRangeFilter(admin.SimpleListFilter):
    title = '评分范围'                 # 侧边栏显示的名字
    parameter_name = 'score_range'     # URL 参数名 → ?score_range=low

    def lookups(self, request, model_admin):
        """下拉框里的选项：(内部值, 显示文字)"""
        return (
            ('low', '低分 (1-3分)'),
            ('medium', '中分 (4-7分)'),
            ('high', '高分 (8-10分)'),
        )

    def queryset(self, request, queryset):
        """根据选中的值过滤数据"""
        if self.value() == 'low':
            return queryset.filter(score__range=(1, 3))
        elif self.value() == 'medium':
            return queryset.filter(score__range=(4, 7))
        elif self.value() == 'high':
            return queryset.filter(score__range=(8, 10))
        return queryset

四个组成部件：title（显示名）→ parameter_name（URL 参数）→ lookups（下拉选项）→ queryset（过滤逻辑）。self.value() 返回当前选中的内部值（low/medium/high 或 None），返回值必须是过滤后的 QuerySet。这是教程 Part 7 知识点里你做得最完整的一块——面试讲 admin 定制时，这就是你的主打故事。

8.1 Q 对象：多条件的"或"查询

reviews/views.py 节选
albums = albums.filter(
    Q(title__icontains=query) | Q(artist__icontains=query)
)
  • 为什么需要 Q？filter 里的多个关键字参数默认是 AND 关系：filter(title__icontains=query, artist__icontains=query) 意思是"标题且艺人都包含关键词"——几乎搜不到东西。要表达"标题或艺人包含关键词"，必须用 Q 对象。
  • 语法：| 或、& 与、~Q(...) 非。例如 Q(title__icontains=query) & ~Q(artist='佚名')。
  • 面试扩展：Q 常用于构建动态搜索条件（多个筛选框组合时，用一个 Q 列表 reduce(operator.or_, conditions) 拼起来）。

8.2 聚合：aggregate 与 annotate 的区别（高频考点）

8.3 模糊查询的底层：icontains 对应什么 SQL

title__icontains='love' 翻译成 SQL 是 WHERE title LIKE '%love%'（大小写不敏感由数据库函数处理）；artist__iexact='周杰伦' 是 WHERE artist = '周杰伦' 的忽略大小写版。能说出「ORM 最终翻译成 LIKE 语句」，面试官就知道你真懂。

8.4 模型方法调外部 API：设计上的讨论

你的 fetch_cover_from_itunes() 放在模型里，有它的道理（方法操作的是自身字段），但也要知道权衡：

  • 优点：简单直接，admin 里一行就能调用；
  • 缺点：模型和外部服务耦合，且 self.save() 绕过了 Django 的表单校验层；网络慢时后台点保存会卡 5 秒（你设了 timeout=5）；
  • 更工程化的做法：把网络请求放进独立的服务模块（如 services.py），或用 Celery 异步任务（你学习计划第 6 周就要学）——现在知道「为什么以后要改」就够了。

面试Part 1–7 高频问答速背版

以下回答都控制在 30 秒能说完的长度，先背框架，再在项目里找例子佐证。

Q1. Django 的 MTV 架构是什么？

M 是模型（models.py，管数据和数据库），T 是模板（templates，管页面展示），V 是视图（views.py，管业务逻辑、把模型和模板连起来）。加一个 URL 分发层（urls.py）。我可以用我的乐评项目举例：Album 模型存专辑数据，album_detail 视图查库算平均分，album_detail.html 负责展示。

Q2. Django 处理一次请求的完整流程？

浏览器发请求 → WSGI 入口 → 项目总路由按 include 分发给应用路由 → path 匹配出视图和参数 → 视图执行业务逻辑、通过 ORM 读写数据库 → render 渲染模板 → 返回 HttpResponse。我的 /album/5/ 就是这个流程的实例。

Q3. blank 和 null 的区别？

blank 管表单校验（允许留空），null 管数据库（允许存 NULL）。字符串字段留空存的是空字符串，所以只写 blank；数字、日期、外键字段要两个都写。

Q4. ForeignKey 的 on_delete 有哪些选项？

CASCADE 级联删除；PROTECT 有引用就禁止删除并抛异常；SET_NULL 置空（需要 null=True）；SET_DEFAULT 设默认值。我的项目里删专辑会级联删掉它的评分，用的 CASCADE。

Q5. 迁移机制是怎么工作的？为什么分两步？

makemigrations 对比模型生成迁移文件（版本化的改动说明），migrate 真正执行并记录到 django_migrations 表。分两步是因为迁移文件是代码，要提交到 Git 供团队共享，别人拉取后自己执行 migrate 同步数据库。

Q6. get 和 filter 的区别？

get 返回单个对象，找不到抛 DoesNotExist 异常，多条匹配也报错；filter 返回 QuerySet，找不到是空集合不报错。可能不存在的场景用 get_object_or_404。

Q7. ORM 查询是立即执行的吗？

不是，QuerySet 是惰性求值：拼条件时不查库，真正迭代、取长度、渲染时才执行 SQL，所以可以链式拼接只发一次查询。

Q8. GET 和 POST 的区别？什么时候用哪个？

GET 参数在 URL 上、可收藏、刷新无害、适合读取（我的搜索用 GET）；POST 参数在请求体、适合写操作，但刷新会重复提交，所以提交成功后要重定向（PRG）。敏感数据不能用 GET 传。

Q9. CSRF 是什么？Django 怎么防？

跨站请求伪造：恶意网站诱导已登录用户向目标站点发请求，浏览器会自动带 Cookie，从而冒用身份操作。Django 在 POST 表单里放一个随会话生成的令牌（{% csrf_token %}），CsrfViewMiddleware 校验它和 Cookie 匹配，伪造站点拿不到令牌就过不了。

Q10. 什么是 PRG 模式？

Post-Redirect-Get：POST 处理成功后返回 302 重定向，浏览器再 GET 一个展示页。防止用户刷新页面重复提交写操作。

Q11. 类视图的 as_view() 做了什么？

把类视图实例化并转成一个可调用的视图函数，内部根据 HTTP 方法分发到 get / post 等方法。路由里写 ClassView.as_view()。

Q12. 函数视图和类视图怎么选？

标准 CRUD（列表、详情、增删改）用通用类视图，少写代码；流程特殊的页面用函数视图更直白。我的项目搜索页和艺人页用函数视图，详情页可以改写成 DetailView。

Q13. 模板里怎么引用 URL？为什么不用硬编码？

路由定义时给 name，模板里用 {% url 'name' 参数 %} 反查。硬编码的话路由一改所有模板都要改；用 name 反查改路由不影响模板。多个应用时加 app_name 命名空间。

Q14. 404 是怎么处理的？

查询不存在的对象时用 get_object_or_404，它捕获 DoesNotExist 后抛 Http404 异常，Django 转成 404 响应；不然会变成 500 错误。

Q15. 为什么写测试？你的项目测了什么？

防止回归、给重构信心、测试本身就是文档。我测了模型 __str__、首页 200 和搜索过滤、详情页 404 和平均分计算等 9 条测试，用 TestCase 的独立临时数据库，一条命令全量跑。

Q16. 开发和生产环境的静态文件有什么不同？

开发时 staticfiles 应用自动服务各应用的 static 目录；生产时 DEBUG=False，Django 不再服务静态文件，需要 collectstatic 收集到 STATIC_ROOT，交给 Nginx 直接服务。

Q17. 你自定义过 admin 吗？

自定义过：列表页加封面缩略图列（自定义方法 + format_html）、覆写 save_model 保存时自动调用 iTunes API 拉封面、写了一个按评分范围过滤的 SimpleListFilter（title/parameter_name/lookups/queryset 四件套），还准备加 fieldsets 分组和评分内联编辑。

Q18. aggregate 和 annotate 的区别？（超纲加分）

aggregate 把整个查询集压成一行汇总，返回字典（我的详情页平均分）；annotate 给查询集每一行加计算列，返回 QuerySet（列表页给每张专辑带平均分就用它，一次查询避免 N+1）。

对照你的《学习计划_寒假实习》，官方教程 Part 1–7 对应第一阶段第 1 周的产出——这一项你已经完成 ✅。按计划，接下来 5 周是：

周次计划内容乐评项目上的落地动作
第 2 周CBV、中间件、用户认证系统加 users 应用：注册/登录/个人中心；UserRating 加 user 外键；评分提交表单（本复习文档第 4 章已画好设计）；login_required 保护页面

第 5 周DRF 进阶（认证、权限、分页、过滤、JWT）API 加 JWT 认证和分页
第 6 周缓存（Redis）、Celery、信号首页缓存；封面抓取改成 Celery 异步任务（正好解决第 8 章说的"后台保存卡 5 秒"问题）

  1. 把本复习文档的练习全部落地：about 页、listens 字段、base.html 继承 + style.css、CBV 改写、tests.py 跑绿、admin 三件套。每完成一项打一个 git commit——你的学习计划里写了「用 Git 管理代码，养成提交习惯」。
  2. 写一篇复盘博客（CSDN/掘金）：《用 Django 做完乐评项目后，我对 Part 1–7 的 18 个问答》——把第 10 章的内容变成文章，既是复习也是学习计划里的「技术博客 10+ 篇」KPI。
  3. 给项目的下一步做设计：用户系统是第 2 周的大工程，先画好「UserRating 怎么关联 User」「哪些页面要登录」再动手。
